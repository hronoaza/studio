## DR-001 — Acquisition identity is currently minted too late

### Current contract

The candidate contract defines:

`EvidenceAcquisitionId`

as generated by D8B trusted code while also defining an acquisition as the
trusted intake of one coherent D8A source snapshot.

### Problem

If the identity represents the **source sample/capture event**, minting it only
when D8B wraps an already-existing D8A snapshot is semantically late.

The same immutable D8A snapshot could otherwise be passed to the D8B producer
twice and receive two different acquisition identities.

That gives this shape:

```text
same D8A snapshot S
 -> D8B acquisition A
 -> D8B acquisition B
```

even though there was only one actual source capture.

This weakens the intended anti-mixing invariant because the identity no longer
names the source acquisition; it names a later envelope-production event.

### Required correction

The identity that means "one coherent source sample" should be minted at the
source-capture boundary.

Candidate name:

`SourceCaptureId`

or, if the acquisition terminology is retained:

`EvidenceAcquisitionId`

with ownership moved to D8A.

Candidate semantics:

```text
D8A capture event
 -> mint SourceCaptureId
 -> capture coherent source facts
 -> immutable SourceSnapshot(SourceCaptureId, ...)
```

D8B then **preserves** that identity. It does not invent a new one.

D8B may independently mint:

`ProvenanceItemId`

for the envelope artifact.

### Resulting identity model

```text
relationship address
!= relationship incarnation
!= source capture identity
!= provenance item identity
!= content digest
```

### Upstream impact

This likely requires a small D8A contract amendment before D8B implementation.

It does **not** require D8A to claim provenance semantics. A capture-event
identity is still source-capture metadata.

PR #8 should not be changed until this review is accepted.

## DR-002 — SHA-256 is a content digest, not authenticated integrity

### Current contract

The candidate envelope contains:

`IntegrityDigest`

computed as SHA-256 over canonical envelope material.

The contract correctly states that this does not authenticate the producer.

### Problem

The name `IntegrityDigest` can still imply a stronger property than exists.

If an attacker or faulty component can rewrite the envelope and recompute the
SHA-256 value, the envelope remains internally self-consistent.

An unauthenticated digest embedded beside the content provides:

- deterministic content identification;
- corruption detection when compared against a trusted expected digest;
- canonical self-consistency checking.

It does not by itself provide:

- origin authentication;
- tamper resistance against an active rewriter;
- trusted integrity unless the digest is anchored outside the mutable object.

### Required correction

Rename the D8B field to a narrower term such as:

`CanonicalDigest`

or:

`EnvelopeContentDigest`.

Retain SHA-256 as the candidate algorithm.

Reserve stronger terms such as:

`AuthenticatedIntegrity`

for a later contract with an independent trust anchor, signature, MAC or
equivalent mechanism.

### Required invariant

```text
canonical_digest_match
!= authenticated_origin
!= trusted_integrity
!= source_truth
```

D8C may check the canonical digest, but it must not treat that check alone as
proof of trusted provenance.

## DR-003 — SourceReference conflates source binding and retrievability

### Current contract

`SourceReference` minimally contains:

- relationship locator;
- relationship generation;
- state version;
- acquisition identity.

A future persistent store may add record/object IDs and retrieval information.

### Problem

The minimum structure is a **binding**, not a dereferenceable source reference.

It identifies the context that produced the envelope but does not necessarily
allow an independent verifier to retrieve the original capture record.

Calling it `SourceReference` risks conflating:

1. source/context binding;
2. persistent source-record identity;
3. source-record retrieval;
4. source re-derivability.

These are distinct properties.

### Required correction

Split the concepts.

#### A. SourceBinding — mandatory

Candidate fields:

- source capture identity;
- relationship address/incarnation;
- state version.

Purpose:

> bind this envelope to the exact capture context.

#### B. SourceRecordReference — optional/future

Only present when a persistent source-capture store actually exists.

Candidate fields may include:

- source-record ID;
- source-record digest;
- storage namespace/object ID;
- retrieval/version metadata.

Purpose:

> enable retrieval or independent reconstruction of retained source material.

### Required invariant

```text
source_binding_present
!= source_record_retrievable
!= source_rederivable
```

D8C may require re-derivability for admissibility, but D8B v1 must not pretend a
relationship/state tuple is a retrievable source record.

## DR-004 — Canonical bytes need one normative preimage with no duplicate fields

### Current contract

The candidate structure contains relationship/state metadata and a canonical
source payload that also lists:

- source/target IDs;
- relationship generation;
- state version.

The digest preimage then includes both the bindings and the canonical payload.

### Problem

This creates two possible representations of the same semantic fields.

Even if an implementation always keeps them equal, the specification should
not create a state in which:

`relationshipBinding.relationshipGeneration != payload.relationshipGeneration`

is representable.

Duplicate canonical ownership also complicates:

- digest definition;
- decoder validation;
- test vectors;
- schema migration.

The current `A || B || C` digest description is also not yet a normative byte
format. Variable-length descriptors require exact framing to prevent ambiguous
concatenations.

### Required correction

Define one canonical envelope preimage in which every semantic field occurs
exactly once.

Recommended conceptual split:

```text
CanonicalEnvelopeV1
├── EnvelopeHeader
│   ├── schema identity/version
│   ├── canonical encoding version
│   ├── producer descriptor
│   └── provenance item identity
├── SourceBinding
│   ├── source capture identity
│   ├── source node ID
│   ├── target node ID
│   ├── relationship generation
│   └── state version
├── SourceMeasurements
│   ├── distance
│   ├── orientation weight
│   ├── capacity
│   ├── bridge status
│   ├── source state
│   ├── source health
│   ├── target state
│   └── target health
└── DependencyManifest
```

Then:

```text
CanonicalDigest = SHA-256(
    domain_separator || canonical_encode(CanonicalEnvelopeV1)
)
```

The digest field itself is excluded from the preimage.

### Framing requirement

The canonical encoder must specify:

- exact field order;
- exact integer widths;
- exact enum tag widths;
- exact floating-point bit encoding;
- exact string/byte-string encoding;
- exact length-prefix width;
- exact list count/order rules;
- exact domain-separator bytes.

No semantic field may have two canonical owners.

## DR-005 — Encode/decode round-trip conflicts with restricted-origin semantics

### Current contract

The verification plan requires:

> envelope survives encode/decode round-trip without semantic drift.

### Problem

If a public decoder can construct a fully trusted
`ProductionProvenanceEnvelope` from arbitrary bytes, restricted-origin
construction can be bypassed.

### Required correction

Choose one of these designs.

#### Option A — no D8B public decoder in v1

D8B only constructs envelopes from restricted-origin D8A snapshots.

Serialization exists only for canonical digest/test-vector purposes.

#### Option B — decoded object is untrusted

Decode into a separate type such as:

`UnverifiedProvenanceEnvelopeBytes`

or:

`DecodedProvenanceEnvelope`

which cannot be consumed as trusted D8B provenance until independent validation
re-establishes the construction invariants.

For v1, Option A is the smaller surface.

## DR-006 — Identity uniqueness domain is underspecified

### Current contract

The acquisition and provenance item IDs must be unique within the producer
identity domain.

### Problem

The contract does not define whether uniqueness must survive:

- process restart;
- machine restart;
- producer-version change;
- multiple producer instances;
- concurrent producers.

A process-local counter can reuse identities after restart.

### Required correction

Define the identity domain before implementation.

Candidate choices include:

- persistent monotonic sequence scoped by stable producer instance;
- random 128-bit identity with collision assumptions explicitly documented;
- composite `producer-instance-id + monotonic-sequence`.

The choice is an implementation/design decision, but the required uniqueness
scope must be explicit.

## DR-007 — Schema/producer/dependency metadata currently overlap

### Current contract

The envelope directly stores:

- producer descriptor;
- schema descriptor;

while the dependency manifest may also list:

- provenance schema;
- producer implementation;
- canonicalization algorithm;
- integrity algorithm.

### Problem

The same dependency can appear in two places with potentially divergent
versions/digests.

### Required correction

Choose one canonical owner for each identity.

Suggested rule:

- direct descriptors are normative for schema and producer identity;
- dependency manifest contains only additional materially participating
  dependencies not already represented by normative envelope header fields.

If a content digest of the schema or producer implementation is required, add
that digest to the normative descriptor rather than duplicating the dependency.

## DR-008 — Canonical test vectors must be normative and externally fixed

### Current contract

The contract already requires fixed test vectors and correctly forbids using
the implementation under test as its own oracle.

### Required refinement

The exact canonical bytes should become part of the design specification before
the C++ producer exists.

At minimum define vectors for:

1. ordinary finite positive values;
2. zero values;
3. negative zero;
4. min/max enum tags;
5. relationship-generation/state-version boundary values;
6. repeated source content with different capture IDs;
7. repeated capture with different provenance item IDs;
8. dependency-manifest order normalization.

NaN/Infinity vectors should exist only if D8A can legally expose them. If D8A
already forbids such values, the canonical contract should state that instead
of specifying unreachable encodings.

## Four design decisions after review

### 1. Acquisition identity

**Decision candidate:** REVISE.

Move source-sample identity to D8A capture. D8B preserves it and mints only the
provenance item identity.

### 2. Canonical bytes

**Decision candidate:** REVISE.

Keep versioned binary encoding, but define one exact canonical envelope preimage
with each semantic field serialized exactly once.

### 3. SHA-256 / domain separation

**Decision candidate:** KEEP WITH NARROWER SEMANTICS.

Keep SHA-256 and explicit domain separation for v1 deterministic content
binding.

Rename `IntegrityDigest` to `CanonicalDigest` or
`EnvelopeContentDigest`.

Do not claim authenticated integrity.

### 4. SourceReference

**Decision candidate:** REVISE.

Split mandatory `SourceBinding` from optional/future
`SourceRecordReference`.

Do not claim source re-derivability until an actual retained source record can
be independently located/reconstructed.

## Revised conceptual D8B shape

```text
D8A capture
  -> SourceCaptureId + coherent immutable SourceSnapshot
  -> D8B producer
      -> ProvenanceItemId
      -> EnvelopeHeader
      -> SourceBinding
      -> SourceMeasurements
      -> DependencyManifest
      -> CanonicalEnvelopeV1 bytes
      -> SHA-256 CanonicalDigest
  -> immutable ProductionProvenanceEnvelope
  -> STOP
```

D8C later decides whether this envelope is admissible.

D8D later interprets admissible provenance.

---

## Architecture invariants after review

```text
one source capture -> one SourceCaptureId

one D8B envelope -> one SourceCaptureId
                 -> one ProvenanceItemId

SourceCaptureId is preserved from D8A, not minted by D8B

every canonical semantic field has exactly one serialized owner

CanonicalDigest binds canonical bytes
but does not authenticate their producer

SourceBinding identifies context
but does not imply source-record retrievability

well_formed_envelope != admissible_provenance
canonical_digest_valid != authenticated_integrity
provenance != interpretation
```

---

## Disposition

The original D8B design is **not rejected**.

Its layer boundary, restricted-origin construction, anti-mixing objective,
prepare-before-publish rule, immutable evidence model and separation from D8C /
D8D / authority remain sound.

However, implementation should not begin until DR-001 through DR-004 are
resolved in the contract.

Recommended next action:

1. accept/reject this review;
2. if accepted, amend `DESIGN_CONTRACT.md` on this candidate branch;
3. produce exact `CanonicalEnvelopeV1` byte layout and fixed vectors;
4. only then design the C++ API.

## Resolution after D8A acceptance

This review remains historical evidence of the defects found in the first D8B
draft.

Its blocking findings were subsequently addressed as follows:

- DR-001: resolved upstream by accepted D8A `SourceCaptureId` in Current
  Baseline `379cd2e2cf17eb7181629945e670f7923ba662ce`;
- DR-002: resolved in the revised contract by narrowing to
  `CanonicalDigest`;
- DR-003: resolved by splitting mandatory `SourceBinding` from future
  `SourceRecordReference`;
- DR-004: resolved by normative `CanonicalEnvelopeV1`;
- DR-005: revised contract does not permit arbitrary decoded bytes to become a
  trusted envelope;
- DR-007: normative producer/schema ownership is separated from additional
  dependency entries;
- DR-008: fixed byte-level conformance vectors now exist.

DR-006 remains open only for the D8B-owned `ProvenanceItemId`.
The D8A-owned capture identity uniqueness decision is already accepted upstream.

Therefore the historical disposition `REVISE BEFORE DESIGN ACCEPTANCE` should
not be read as the current PR #12 disposition.
