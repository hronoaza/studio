# SOAM 2.0 D8B — Provenance Envelope Design Contract

## Status

- Layer: D8B — Provenance Envelope
- Document class: design-contract candidate
- Executable implementation: none
- Current Baseline effect: none
- Acceptance status: design-review pending
- Upstream dependency: D8A Source Capture candidate (PR #8)
- Downstream dependency: future D8C Provenance Admissibility
- Authority effect: none

This document defines the candidate contract for converting one trusted D8A
source snapshot into one immutable provenance-bearing envelope.

It deliberately does **not** implement provenance admissibility,
interpretation, transition eligibility, authority, capability issuance or
commit.

---

## 1. Boundary

D8B begins with exactly one restricted-origin D8A value:

`ProductionRelationshipSourceSnapshot`

and ends with exactly one restricted-origin provenance envelope:

`ProductionProvenanceEnvelope`

Conceptual chain:

`ProductionRelationshipLocator
-> D8A ProductionRelationshipSourceSnapshot
-> D8B ProductionProvenanceEnvelope
-> STOP`

D8B MUST NOT produce:

- `InteractionObservation`;
- `BridgeConfidence`;
- `BridgePolicyEvidence`;
- `RequestedTransitionDirection`;
- `eligible_for_authority_consideration`;
- execution capability;
- production commit.

A D8B envelope is provenance-bearing evidence, not admissible evidence.

---

## 2. Core distinction: relationship, state, acquisition, item

D8B must keep four identities distinct.

### 2.1 Relationship address

`ProductionRelationshipLocator`

Meaning:

> which directed relationship was requested?

This is descriptive addressing only.

### 2.2 Relationship incarnation

Candidate tuple:

`(sourceNodeId, targetNodeId, relationshipGeneration)`

Meaning:

> which concrete lifetime/incarnation of that relationship supplied the facts?

A recreated relationship with the same endpoint IDs is a different incarnation.

### 2.3 Acquisition identity

Candidate type:

`EvidenceAcquisitionId`

Meaning:

> which trusted intake of one coherent D8A source snapshot is this evidence
> derived from?

Properties:

- generated by D8B trusted code;
- not caller-selectable;
- immutable;
- unique within the producer identity domain;
- never inferred from payload equality;
- never reused after failure or publication.

The acquisition identity binds downstream derivations to one source sample.

Two byte-identical snapshots wrapped in two separate acquisitions MAY have
different `EvidenceAcquisitionId` values.

### 2.4 Provenance item identity

Candidate type:

`ProvenanceItemId`

Meaning:

> which immutable provenance artifact is this?

Properties:

- generated by the D8B producer;
- not caller-selectable;
- stable for the lifetime of the envelope;
- distinct from the acquisition identity and integrity digest.

One future acquisition may legitimately produce more than one typed provenance
item. Therefore acquisition identity and item identity must not be collapsed.

---

## 3. One-acquisition rule

The principal D8B invariant is:

`one envelope -> one acquisition -> one coherent D8A source snapshot`

D8B must not accept separately supplied:

- observation;
- confidence;
- bridge recommendation;
- cached policy evidence;
- relationship generation;
- state version;
- endpoint state;
- bridge state

when those fields are already owned by the D8A snapshot.

All raw relationship facts used by the envelope must come from the same
restricted-origin D8A value.

This prevents a caller from constructing an apparently coherent provenance item
from facts captured at different times or from different relationship
incarnations.

---

## 4. Anti-mixing invariant

For any downstream derivation that claims to represent one sample:

`all contributing facts must share the same EvidenceAcquisitionId`

D8D must not be able to combine:

`Observation(acquisition A)`

with:

`Confidence(acquisition B)`

and present the result as one coherent sample.

If a future operation intentionally aggregates multiple acquisitions, it must
use a separate aggregate type that explicitly carries:

- all contributing acquisition IDs;
- aggregation policy ID/version;
- ordering semantics where relevant;
- aggregate derivation identity.

Multi-acquisition aggregation is outside D8B v1.

---

## 5. Candidate envelope structure

Conceptual structure only:

```text
ProductionProvenanceEnvelope
├── ProvenanceItemId itemId
├── EvidenceAcquisitionId acquisitionId
├── ProducerDescriptor producer
├── ProvenanceSchemaDescriptor schema
├── RelationshipBinding relationship
│   ├── sourceNodeId
│   ├── targetNodeId
│   └── relationshipGeneration
├── StateBinding state
│   └── stateVersion
├── CanonicalSourcePayload payload
├── SourceReference sourceReference
├── DependencyManifest dependencies
└── IntegrityDigest integrity
```

The exact C++ spelling is not accepted by this document.

---

## 6. Source payload

The D8B v1 payload is a canonical serialization of the raw facts exposed by the
accepted D8A contract.

Candidate fields:

- source node ID;
- target node ID;
- relationship generation;
- runtime state version;
- distance;
- orientation weight;
- capacity;
- bridge status;
- source endpoint state;
- source endpoint health;
- target endpoint state;
- target endpoint health.

D8B must preserve these as source facts.

In particular, D8B must not interpret `BridgeStatus` as:

- requested direction;
- compatibility;
- confidence;
- permission;
- authority.

---

## 7. Canonical encoding

Integrity must never depend on:

- in-memory struct layout;
- padding bytes;
- compiler ABI;
- native endianness;
- `std::hash`;
- locale-dependent number formatting;
- JSON key iteration order;
- unspecified enum representation.

D8B therefore requires a versioned canonical binary encoding.

### 7.1 Candidate v1 encoding rules

- fixed schema-controlled field order;
- unsigned integer widths explicitly defined;
- integers encoded network-order / big-endian;
- enum values mapped to schema-defined integer tags;
- floating-point source values encoded as their IEEE-754 binary64 bit pattern;
- no locale or text conversion;
- field presence is explicit;
- length-delimited variable fields;
- canonical domain separator included before payload bytes.

For source floating-point facts, D8B v1 preserves the captured bit pattern. It
does not silently normalize:

- negative zero;
- infinities;
- NaN payloads.

Whether such values are admissible is a D8C decision.

This prevents D8B canonicalization from becoming hidden semantic
interpretation.

---

## 8. Schema identity

Candidate descriptor:

```text
ProvenanceSchemaDescriptor
- schemaId
- majorVersion
- minorVersion
- canonicalEncodingVersion
```

The schema identity defines:

- field set;
- field order;
- primitive encodings;
- enum tags;
- required/optional fields;
- canonicalization rules.

A schema version change that changes canonical bytes must be explicit.

D8B does not decide whether a schema is acceptable for current production.
That is D8C.

---

## 9. Producer identity

Candidate descriptor:

```text
ProducerDescriptor
- producerId
- producerVersion
- implementationRevision
```

Producer identity states which trusted D8B implementation created the envelope.

It is not, by itself, authentication.

D8B v1 does not claim that a textual producer ID proves origin.

Future authentication may bind a producer identity to a signature/key or other
attestation mechanism, but that belongs to an independently reviewed contract.

D8C may reject unknown or untrusted producers.

---

## 10. Source reference

Candidate `SourceReference` must be sufficient to identify what source
material the envelope claims to represent.

At minimum it binds:

- relationship locator;
- relationship generation;
- runtime state version;
- acquisition identity.

A future persistent source store may add:

- capture-record ID;
- archive/object ID;
- source digest;
- retrieval location/reference.

D8B v1 must distinguish two properties:

### Integrity reproducibility

Can the envelope digest be recomputed from the envelope itself?

### Source re-derivability

Can the source material or derivation be independently reconstructed from
retained source/reference material?

The first is a D8B property.

The second is a D8C admissibility question and may fail even when envelope
integrity is valid.

---

## 11. Dependency manifest

Candidate type:

`DependencyManifest`

The manifest lists only dependencies that materially participated in producing
the envelope.

Candidate dependency kinds:

- source-capture contract;
- provenance schema;
- canonicalization algorithm;
- producer implementation;
- integrity algorithm.

D8B must not fabricate dependencies for later interpretation/authority layers
that did not participate in envelope construction.

Each dependency reference should contain:

- dependency kind;
- stable ID;
- version/revision;
- optional content digest when meaningful.

Canonical manifest ordering must be defined by schema.

Whether a dependency is current, retired or prohibited belongs to D8C.

---

## 12. Integrity binding

D8B v1 candidate integrity algorithm:

`SHA-256`

This choice is for deterministic integrity binding, not authentication.

Candidate digest input:

```text
domain_separator
|| schema descriptor
|| producer descriptor
|| provenance item ID
|| acquisition ID
|| relationship binding
|| state binding
|| source reference
|| dependency manifest
|| canonical source payload
```

The integrity digest therefore binds both payload and identity/lineage metadata.

Required domain separator candidate:

`SOAM:D8B:PROVENANCE-ENVELOPE:V1`

The exact byte encoding of the separator is part of the schema.

### Security boundary

A matching SHA-256 digest proves only that the recomputed bytes equal the bytes
that were originally digested.

It does not prove:

- producer authenticity;
- source truth;
- admissibility;
- freshness;
- authorization;
- absence of malicious input.

Those are separate checks.

---

## 13. Construction authority

`ProductionProvenanceEnvelope` must be restricted-origin.

Candidate rule:

- no public aggregate initialization;
- no public constructor accepting arbitrary raw fields;
- no public constructor accepting an arbitrary digest;
- caller cannot supply `ProvenanceItemId`;
- caller cannot supply `EvidenceAcquisitionId`;
- caller cannot claim a producer identity.

Only the accepted D8B producer/factory may construct the envelope from an
authentic D8A source snapshot.

A forged-envelope compile-fail gate is required before acceptance.

---

## 14. Publication model

D8B construction should follow:

`capture input
-> prepare detached canonical bytes
-> prepare detached metadata
-> compute digest
-> validate internal construction invariants
-> publish immutable envelope`

Potentially throwing work must happen before authoritative publication.

D8B v1 publication must not mutate:

- live mesh topology;
- relationship lifecycle;
- bridge persistence;
- authority ledger;
- production state.

Envelope publication is evidence creation, not production-state commit.

---

## 15. Immutability

After successful D8B construction:

- payload is immutable;
- identity metadata is immutable;
- dependency manifest is immutable;
- digest is immutable.

Corrections or superseding evidence create a new provenance item.

They do not rewrite the old item.

This supports future append-only evidence-ledger semantics.

---

## 16. Equality semantics

D8B must not collapse all equality into one operator.

At least three comparisons are conceptually distinct:

### Same provenance item

`itemId equal`

### Same acquisition

`acquisitionId equal`

### Same canonical source content

`canonical source payload bytes equal`

Two items may contain identical source content while representing different
acquisitions.

A digest must not be used as a substitute for every identity relation.

---

## 17. Failure semantics

D8B construction must fail closed.

Candidate failure categories:

- unavailable source snapshot;
- invalid internal source binding;
- unsupported schema;
- canonicalization failure;
- identity allocation failure;
- dependency-manifest construction failure;
- digest computation failure;
- publication failure.

On failure:

- no partial envelope is observable;
- no item/acquisition identity may later be reused as if publication succeeded;
- no downstream admissibility/interpretation is possible;
- live production state remains unchanged.

Exact error representation is deferred to implementation design.

---

## 18. D8B does not establish admissibility

A correctly formed D8B envelope may still be rejected by D8C.

Examples:

- producer unknown;
- schema obsolete;
- dependency retired;
- source reference unavailable;
- source cannot be re-derived;
- lineage stale;
- integrity mismatch after storage/transport;
- required external authenticity evidence absent.

Therefore:

`well_formed_envelope != admissible_provenance`

and:

`integrity_valid != source_true`

---

## 19. D8B does not establish interpretation

D8B must not calculate or store semantic fields such as:

- compatibility score;
- observation score;
- confidence score;
- requested direction;
- recommendation;
- authority decision.

Therefore:

`provenance != interpretation`

D8D owns versioned interpretation after D8C admissibility.

---

## 20. Candidate API shape

Non-binding sketch:

```cpp
class ProductionProvenanceEnvelope;

class ProductionProvenanceEnvelopeProducer final {
public:
    ProductionProvenanceEnvelope produce(
        const ProductionRelationshipSourceSnapshot& snapshot);
};
```

The accepted implementation may instead use a free function, factory or
internal owner.

The architectural requirements are:

- restricted-origin input;
- restricted-origin output;
- no caller-supplied identity;
- no caller-supplied digest;
- no interpretation;
- deterministic canonical representation.

---

## 21. Verification plan

D8B implementation acceptance requires at least the following tests.

### Positive tests

1. one valid D8A snapshot produces one envelope;
2. relationship generation/state version are preserved exactly;
3. repeated digest computation over one envelope is identical;
4. canonical encoding is deterministic across repeated runs;
5. envelope survives encode/decode round-trip without semantic drift.

### Negative tests

6. public caller cannot construct a forged envelope;
7. public caller cannot select item/acquisition identity;
8. public caller cannot inject an arbitrary digest;
9. changing any canonical payload field changes integrity result;
10. changing relationship generation changes integrity result;
11. changing state version changes integrity result;
12. changing acquisition ID changes integrity result;
13. changing schema/producer/dependency metadata changes integrity result;
14. mixed-acquisition single-sample derivation is rejected by type/API design;
15. D8B cannot manufacture `InteractionObservation` or `BridgeConfidence`.

### Failure/exception tests

16. identity-allocation failure publishes no envelope;
17. canonicalization failure publishes no envelope;
18. manifest-construction failure publishes no envelope;
19. digest failure publishes no envelope;
20. failed production leaves live runtime state unchanged.

### Portability tests

21. canonical test vectors have exact expected bytes;
22. canonical digest test vectors have exact expected SHA-256;
23. same vectors match across supported compilers/platforms;
24. public D8B declarations are configuration-invariant.

---

## 22. Test vectors as specification evidence

The canonical encoding contract must ship with fixed test vectors.

Each vector should include:

- human-readable source fields;
- expected canonical byte sequence;
- expected digest;
- schema version;
- producer descriptor;
- acquisition/item identities.

This converts canonicalization from prose into regression-testable evidence.

The vectors must not be generated dynamically by the same code under test and
then treated as an independent oracle.

---

## 23. Concurrency/lifetime boundary

D8B v1 should prefer construction from an already captured immutable D8A
snapshot.

It should not hold the mesh topology lock while:

- allocating envelope storage;
- serializing canonical bytes;
- building manifests;
- computing digests;
- performing external callbacks.

No external provider callback is permitted while a live mesh topology lock is
held.

The D8A snapshot is the lock-boundary handoff.

---

## 24. Relationship to the independent audit evidence

The older audited implementation identified a provenance gap: already-composed
policy evidence could be supplied without an acquisition/sample identity,
allowing observation/confidence from different semantic samples to be combined
before a later CAS check.

D8B addresses that class of design defect structurally by:

- binding one envelope to one D8A snapshot;
- minting one acquisition identity;
- prohibiting caller-composed policy evidence at this layer;
- requiring downstream one-sample derivation to retain acquisition identity.

This document does not claim that the older audited implementation satisfies
this contract.

---

## 25. Relationship to Architecture Candidate Register

The D8B contract concretizes, but does not automatically accept, the following
candidate concepts:

- provenance integrity binding;
- append-only evidence identity;
- source/context binding;
- canonicalized immutable representation;
- context-bound artifacts.

Numeric or algorithm choices in this document remain candidate decisions until
the D8B design itself is accepted.

---

## 26. Non-goals

D8B v1 explicitly excludes:

- digital signatures;
- key management;
- remote attestation;
- trust-store governance;
- schema-compatibility policy;
- retired-dependency policy;
- source-truth verification;
- semantic interpretation;
- confidence calibration;
- transition eligibility;
- authority;
- capability issuance;
- execution;
- rollback;
- production commit.

These exclusions prevent D8B from becoming another monolithic provenance layer.

4. canonical encoding rules must be accepted;

## 28. Candidate invariants summary

```text
one envelope -> one acquisition -> one coherent D8A snapshot

relationship address != relationship incarnation
relationship incarnation != acquisition identity
acquisition identity != provenance item identity
identity != digest

well_formed_envelope != admissible_provenance
integrity_valid != source_true
provenance != interpretation
accepted != active

all source facts in one envelope come from one restricted-origin snapshot

all potentially throwing preparation occurs before envelope publication

failed D8B construction publishes no partial envelope
and mutates no live production state
```
